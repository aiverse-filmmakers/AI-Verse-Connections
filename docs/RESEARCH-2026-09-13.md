# Public-beta research pass — 2026-09-13

This implementation was designed after a fresh pass over the current AI-Verse public-beta contracts and the current Model Context Protocol release.

## AI-Verse laws carried into v1

Connections is the owner of external connection identity, credential handles, provider adapters, connection health/revocation, capability grants and the final external execution boundary.

Connections does not become the scheduler, Brain, Skills, Gateway, Dashboard, OS policy source of truth, or a local canonical copy of third-party SaaS data.

The implementation preserves these system laws:

- registration is not authorization;
- live verification is not approval;
- integrity/availability does not imply trust;
- system/workspace/delegated authority can only narrow access;
- external side effects re-check current authority at the final provider edge;
- agents receive connection/capability handles rather than raw credentials;
- external provider data remains externally canonical unless a separate sync contract explicitly says otherwise.

## Current MCP baseline

The current released MCP specification is **2026-07-28**.

Important implementation consequences:

1. The core protocol is stateless. The old `initialize` / `notifications/initialized` handshake and `Mcp-Session-Id` are removed for this revision.
2. Servers must implement `server/discover`; clients can use it to retrieve supported protocol versions and capabilities.
3. Every HTTP request carries `MCP-Protocol-Version`, and Streamable HTTP requests carry `Mcp-Method`. `tools/call` also carries `Mcp-Name`.
4. Request `_meta` carries protocol version and client capabilities. Server identity is self-reported metadata and must not be treated as security identity.
5. `tools/list`, `resources/list`, and related list/read results are cache-aware. AI-Verse does not trust cache freshness for authority and re-verifies catalogs explicitly.
6. Authorization is OAuth-aligned. Resource-bound tokens and audience validation are core security requirements. Token passthrough is forbidden. Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents.
7. Roots, Sampling and Logging are deprecated in the 2026-07-28 core. Connections v1 does not build new dependencies on those features.

## MCP v1 admission model

An MCP server URL/origin can be registered without granting any tool authority.

Verification performs:

1. `server/discover` against MCP `2026-07-28`;
2. protocol-version validation;
3. `tools/list` discovery;
4. `resources/list` discovery when resources are advertised;
5. deterministic fingerprints for each tool and resource catalog;
6. capture of self-reported server identity separately from the canonical registered origin;
7. prompt-injection/tool-poisoning signal detection on server instructions and tool descriptions.

New tools are not admitted automatically.

A user/operator must explicitly map each desired MCP tool to an AI-Verse capability and risk class. The connection must then be approved. A changed tool descriptor/schema is treated conservatively as a permission-relevant change: its admission is cleared and connection approval is revoked until review.

This intentionally prefers false-positive review over silently accepting broader tool authority.

## MCP authorization scope in v1

Connections v1 supports HTTP MCP servers with either:

- no authorization; or
- a bearer access token resolved from an opaque credential handle at execution time.

The credential handle can resolve through the encrypted local vault or environment backend. The bearer secret is never stored in the connection registry or execution receipt.

For bearer-authenticated MCP connections, v1 records the intended OAuth resource and forbids reuse of the same credential handle across different MCP origins. Interactive browser OAuth acquisition / Client ID Metadata Document registration is intentionally not implemented in this first minimal release. A token acquired by the proper external authorization flow can be installed/replaced through the credential backend, and `reauth` forces fresh live verification and approval.

## Generic authenticated API path

The second v1 path is a provider-neutral authenticated HTTP API connection.

Controls:

- HTTPS required by default;
- private/reserved/localhost targets blocked by default, including DNS resolution to private addresses;
- explicit origin pinning;
- redirects disabled;
- caller-supplied Authorization/Cookie/API-key transport headers rejected;
- explicit method and path-prefix allowlists;
- bearer or explicit custom-header credential injection only inside the trusted adapter;
- bounded request/response sizes and timeouts;
- live read-only health probe before the connection becomes `liveVerified` / `healthy` / `authorized`;
- external results labeled `untrusted_external`.

Private-network access exists only as an explicit connection setting for controlled environments and integration tests.

## Prompt injection and tool poisoning

MCP metadata and all external results are untrusted input.

Connections v1 therefore:

- never auto-admits discovered MCP tools;
- marks MCP descriptions/instructions as untrusted metadata;
- scans common instruction-like attack patterns and surfaces security signals;
- does not interpret tool output as policy or new authority;
- does not auto-execute nested actions suggested by a result;
- marks every external result with an explicit trust label and provenance;
- requires permission review after tool metadata/schema changes.

The MCP specification itself warns that tool metadata and annotations are not inherently trusted and that tool invocation requires robust consent, access control, rate limiting and output validation.

## Final-edge authority

The execution path checks authority once during planning and again immediately before entering the provider adapter.

The second check reloads the canonical registry, so any intervening revoke, disable, scope change, capability change or approval loss blocks the call.

A planned action cannot carry stale authority across the final edge.

## Idempotency

When an idempotency key is supplied, Connections writes an append-only pending reservation before the external request. A concurrent duplicate cannot enter the provider edge. Successful or provider-error terminal receipts are replayed rather than re-executed.

This is deliberately conservative for uncertain external-side-effect outcomes.

## Deferred beyond minimal v1

The following are not claimed as public-beta v1 features:

- broad provider catalog;
- interactive OAuth browser/client registration UX;
- MCP stdio servers;
- legacy 2025 MCP session/initialize compatibility;
- MCP Tasks extension;
- notification subscriptions;
- external trigger ingestion;
- provider-data synchronization into AI-Verse Data;
- multi-user/team identity and SSO;
- managed integration vendors such as Nango/Pipedream/Composio.

Those can be added behind the same connection/credential/capability boundaries without weakening v1 security semantics.
